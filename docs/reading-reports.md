# Reading a report

Every published run in [`results/`](../results/) has a `report.md`, generated by `avg publish`
from the files beside it and never edited by hand. This page says what each part of a report is
and how its numbers are made. Why the benchmark measures these things is in
[design.md](design.md).

## What a run is

A run takes the first N items of a task's input file and gives every item to every arm. Each arm
does the same job (for task 1, turn a product listing into a validated catalog record) in its own
shape. Every model request goes through the meter, which records its tokens to the run's
`ledger.jsonl`; each arm's output for each item is in `<arm>.jsonl`. Scores come from comparing
those outputs with the gold answers, and costs from pricing the ledger afterwards.

The runs are made on a local GPU with open models, so they cost nothing to reproduce. The money
figures are what the same tokens would cost at each vendor's published prices. Token counts are
the local model's, counted by its own tokenizer; a hosted model would count the same text
somewhat differently, so the figures are a like-for-like comparison between arms, not a quote.

## Arms

An arm's name says its shape and its model:

| Name | Shape |
| --- | --- |
| `graph-<model>` | A workflow graph: fixed steps, each run over every item, every step on that model. |
| `graph` | The same graph with the easy steps (extract, describe) on the small model and repairs on the large one. |
| `agent-<model>` | One tool-calling agent per item on that model, deciding its own steps, with the validator as a tool. |
| `claude-code`, `hermes` | A general-purpose agent harness handed the whole input file at once. |

`graph-12b` and `agent-12b` differ only in shape, which is why the report compares them item by
item.

## Conditions

The conditions every arm in the run shared, from the run's `meta.json`:

| Setting | Meaning |
| --- | --- |
| `limit` | Items in the run: the first N of the task's input file. |
| `slots` | Requests a per-item arm keeps in flight at once. Changes speed, not tokens. |
| `thinking` | `0`: the model answers without a thinking phase. N: it may think for up to N tokens per reply first. |
| `max_tokens` | The cap on one reply, thinking included. A reply that reaches it is cut off. |
| `llama_server` | The llama.cpp build that served the models. |
| `small`, `large` | The two model files. |
| `harness_ctx` | The context window given to the whole-file harnesses. |
| `code` | The commit of this repo the run used. |

## Scores

| Column | Meaning |
| --- | --- |
| Items | Items the arm returned a result row for. |
| Valid | Share of items whose record passes the shared validator (the record spec, plus the check that it was written rather than copied from the listing). An item with no record is not valid. |
| Brand | Share of items whose brand matches the catalog's own brand field. |
| Color | Share matching the catalog's color, over the items that have one. Reported, not part of success. |
| Success | Share of items both valid and with the right brand. |

## Tokens per item

| Column | Meaning |
| --- | --- |
| Items | Items with at least one answered request (for a whole-file harness, the items it was handed). |
| Requests / item | Answered model requests per item. |
| Prompt | Input tokens per item, everything sent, cached or not. |
| Output | Generated tokens per item, thinking included. |
| Refused requests | Requests the server answered with an error, in total. They report no usage, so they are not priced. |

## Price tables

One table per price in [`prices/default.yaml`](../prices/default.yaml), each naming its source
page and the date it was checked. A price marked **Unverified** could not be confirmed on the
vendor's own page and says what to check.

| Column | Meaning |
| --- | --- |
| Mode | `real-time`: the vendor's normal price. `batch`: its batch price, usually half, for work that can wait. Only graph arms are priced as batch, because an agent's requests depend on each other's answers. A vendor that sells only batch has no real-time rows. |
| Cached | Share of prompt tokens the vendor's prompt cache would have served, replayed over the recorded prompts under that vendor's rules (minimum length, lifetime). Cached tokens are billed at the vendor's lower cached rate. |
| Success | The arm's success rate, from the scores. |
| Per 1,000 items | Mean cost per item, times 1,000. |
| Per 1,000 successes | Cost per 1,000 items divided by the success rate: what 1,000 correct records cost when failures are paid for too. |
| p95 item | The cost of the item at the 95th percentile: one expensive item, not an average. |
| N / month | Mean cost per item times N, with its 90% interval in brackets. |
| Year | Twelve months at the largest volume. |

## Graph against agent, item by item

Each `graph-<model>` arm next to `agent-<model>`, over the items both ran.

| Column | Meaning |
| --- | --- |
| Only graph right, only agent right | Items one arm succeeded on and the other did not. Items both got right, or both wrong, say nothing about which is better. |
| Success, graph − agent | The difference in success rate, in percentage points, with its 90% interval. Positive: the graph succeeded more often. |
| p | McNemar's exact test: the chance of a split between the two counts at least this uneven if the arms were equally good. Small p means the difference is unlikely to be chance. |
| Graph − agent, per 1,000 items | The mean per-item cost difference, times 1,000, with its 90% interval. Negative: the graph costs less. The agent is always priced real-time. |
| Relative | That difference as a share of the agent's cost. |

## Intervals

Every interval is a 90% bootstrap interval: resample the run's items 2,000 times (seeded, so a
report regenerates identically) and take the middle 90% of the results. It says how sure the
sample makes us of the average. It does not say how much a real month's bill would vary; that
depends on the mix of work, which no sample can know.

## Checking a report yourself

Everything in a report can be regenerated from the files beside it:

```
avg score results/<run>/<arm>.jsonl ... --out scores.json
avg report results/<run>/ledger.jsonl --scores results/<run>/scores.json
```

Change `--prices` to price the run at your own rates, or `--volume` to project to your own volume.
